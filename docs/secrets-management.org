#+title: Secrets Management
#+author: Pete 'Peteches' McCabe

* Overview

Secrets (API tokens, passwords, Tailscale auth keys, etc.) are encrypted with
[[https://getsops.io/][SOPS]] using [[https://age-encryption.org/][age]] public-key encryption.  Each VM has a unique age keypair; SOPS
encrypts secrets so only the intended recipient VM(s) can decrypt them at boot.

The =sops-guix= channel provides =sops-service-type=, which is wired into VMs via
the =sops-secrets= parameter of =make-vm-os= in =peteches/systems/vm-base.scm=.

* Directory structure

#+begin_example
.sops.yaml              ← encryption rules (path regex → age recipients)
age-keys/               ← age public keys, one per VM
secrets/
  hosts/
    <vm-name>/          ← per-host encrypted YAML files
  groups/
    concourse/          ← secrets shared by the Concourse cluster
    media/              ← secrets shared by media-stack VMs
  shared/
    tailscale.yaml      ← Tailscale auth key (shared)
    peteches-automation-ssh-pub.yaml ← public half of the fleet automation
                                        keypair, accepted by every VM (see
                                        "The peteches automation SSH keypair")
#+end_example

* Age keys

Each VM generates its own age keypair on first boot (via the SOPS key generator
service in =vm-base.scm=).  The public key is committed to =age-keys/<vm-name>.pub=
so that new secrets can be encrypted for that VM without needing its private key.

The private key lives only on the VM itself (=/etc/age/key.txt= or similar);
it is never committed.

** Adding a key for a new VM

After the VM's first boot, retrieve and commit its public key:

#+begin_src bash
ssh <vm-name> cat /etc/age/key.txt | age-keygen -y   # prints public key
# DO NOT echo the private key — store only the public key:
# age-keys/<vm-name>.pub
#+end_src

Then add the appropriate =creation_rules= entry to =.sops.yaml=.

* Editing secrets

#+begin_src bash
sops secrets/hosts/<vm-name>/foo.yaml      # opens $EDITOR, re-encrypts on save
sops secrets/groups/media/credentials.yaml
#+end_src

SOPS reads encryption rules from =.sops.yaml= automatically.  The PGP key
=5FFB7006A36B0AEDE8D08E3753B1E002546A642A= (peteches operator key) is always
included as an additional recipient so secrets remain accessible from the
developer machine.

* Wiring secrets into a VM OS config

In the VM's system file, pass =sops-secrets= to =make-vm-os=:

#+begin_src scheme
(make-vm-os
  ...
  (sops-secrets (list "secrets/hosts/myvmname/foo.yaml")))
#+end_src

The =sops-service-type= will decrypt those files at activation time and make them
available to services on the VM.

* Group secrets

Some secrets are shared across multiple VMs.  Groups are defined in =.sops.yaml=
with a list of age recipients:

- =secrets/groups/concourse/= — shared by =concourse-web01= (other Concourse nodes
  get what they need via the web node)
- =secrets/groups/media/= — shared by jellyfin, prowlarr, arr, downloads, rustdesk

* Shared secrets

=secrets/shared/tailscale.yaml= contains the Tailscale auth key used by VMs that
run Tailscale.  It is encrypted for all Tailscale-enabled VM recipients.

* The peteches automation SSH keypair

One keypair unlocks the =peteches= login on the entire fleet, so it is worth
spelling out where each half lives and who can read it — the code refers to it
from =vm-base.scm=, =common.scm=, =agents.scm= and =machines.scm=, and until
2026-11-05 this document said nothing about it at all.

- *Public half* — =secrets/shared/peteches-automation-ssh-pub.yaml=, encrypted for
  every VM age key listed in =.sops.yaml='s =secrets/shared/.*\.yaml$= rule — 22
  recipients as of 2026-11-05 — plus the operator PGP key.
  =vm-base.scm='s =%automation-authorized-key-secret= decrypts it on *every* VM
  into =/run/secrets/peteches-automation-ssh-key.pub= and authorizes it *for
  the =peteches= login only*, through an sshd =Match User peteches= block — an
  outbound automation identity, never a =sudo= credential, so holding the
  private key buys you logins, not root. Pass =#:with-automation-key? #f= to
  =make-vm-os= for a VM that must not trust it.

  Coverage belongs to the rule, not to =age-keys/=: a VM whose age key is
  missing from that rule quietly fails to decrypt this file at boot, and the
  mere existence of =age-keys/<vm>.pub= proves nothing. Audit it by counting,
  which prints only file names:

#+begin_src bash
python3 - <<'PY'   # committed age keys that are NOT recipients of the shared rule
import yaml,re,glob,os
r=[x for x in yaml.safe_load(open('.sops.yaml'))['creation_rules']
   if x['path_regex']=='secrets/shared/.*\.yaml$'][0]
rec={t for a in (r.get('age') or []) for t in re.findall(r'age1[0-9a-z]+', str(a))}
for f in sorted(glob.glob('age-keys/*.pub')):
    if open(f).read().strip() not in rec: print(os.path.basename(f))
PY
#+end_src

  On 2026-11-05 it printed =dagon.pub= and =jellyfin.pub=, for two different
  reasons. =dagon= is expected — a desktop is not a =make-vm-os= VM and reaches
  every secret through the PGP recipient instead. =jellyfin= was real drift and
  has been fixed in the same commit: that VM was rebuilt on 2026-10-27, its live
  =/etc/age/keys.pub= (the per-VM own age key; there is no =keyring.pub= on that
  box) changed, and the committed file was left behind — while =.sops.yaml='s
  rule and every already-encrypted =secrets/shared/= file carried the *live*
  key, so the VM kept decrypting at boot and the mismatch was invisible from
  there. =age-keys/jellyfin.pub= was then re-fetched from the box over an ssh
  connection verified against =machines.scm='s pinned host key, so the committed
  file and the live file now hash identically. Two lessons for the next
  operator: refresh =age-keys/<vm>.pub= after **any** VM rebuild — the
  =%authorize-coordinator-key= list has to be re-verified for the same event —
  and treat "the VM decrypts its secrets fine" as evidence about the *live*
  key, never about the committed file. The same recount also showed the shared
  rule carries age keys that have no committed =age-keys/= file at all, so a
  recipient audit against =age-keys/= can never be complete.
- *Private half* — =secrets/hosts/agents/peteches-automation-ssh.yaml=, moved from
  =secrets/hosts/claude-workstation/= on 2026-11-05 (that box is a pure
  WireGuard/SOCKS jump box now and keeps no outbound identity; its
  =criticalgrind= and =ygo= accounts, which used =#:automation-key-extra-users=
  to accept this key, are gone). =agents.scm='s =#:sops-secrets= entry decrypts
  it to =/run/secrets/peteches-automation-ssh-key= owned read-only by
  =peteches=, and =machines.scm='s =%deploy-identity= resolves to that path —
  which is what makes fleet deploys runnable from that box. The key is handled
  as a *path*, never a value: nothing copies it into the world-readable
  =/gnu/store=, ssh reads it from tmpfs at connect time. An API key has no such
  option — it must be exported into a service's environment, so anything in
  that closure can read it — which is why the =.env= files below are a slightly
  different risk class from this one.

Moving a secret like this between hosts is a three-step operation and the
order is not optional, because sops cannot widen a file's recipients on its
own — =updatekeys= re-encrypts for whatever =.sops.yaml= says *at the moment
you run it*:

1. fix the =.sops.yaml= rule first (or delete the now-unneeded one — rule order
   is load-bearing, see the comment at the end of that file),
2. =git mv= the file so =git log --follow= still shows its whole history,
3. =sops updatekeys -y <file>=, which re-encrypts for the new recipient set and
   rewrites the file's =sops:= tree — that diff is expected, not a corrupted
   secret.

Two facts about =updatekeys= that the recipe depends on, both verified
2026-11-05: it resolves the creation rule **by the file's path**, so copying a
secret to a path that matches no rule (=/dev/shm= for a dry run, say) fails with
=error loading config: no matching creation rules found= rather than doing
nothing useful; and it must *decrypt* the file before it can re-encrypt it, so
it exits 128 on any file the operator is not a recipient of. Not every
=secrets/hosts/<vm>/= file is — audit a file's recipient groups before planning
any edit of it:

#+begin_src bash
sed -n '/^sops:/,$p' <file> | grep -oE '^ *(age|pgp):' | sort | uniq -c
#+end_src

The known case is =secrets/hosts/claude-workstation/guix-build.yaml=: it has an
=age:= group and no =pgp:= group at all, so from any desktop neither =sops -d=
nor =sops updatekeys= touches it. That is a live liability, not curiosity — if
that VM is ever rebuilt and its age key changes, the file cannot be re-keyed
for the new key from here, and its build-offload secret is unrecoverable until
somebody decrypts it on the box itself.

Then verify. Two gotchas first, learned the hard way during this move:
there is *no* =sops file= subcommand in sops 3.13 (=filestatus= reports only
encryption status), and the stored recipient list lives in the file's own
cleartext =sops:= tree — so check it by *counting*, never by printing age
keys, which this repo's no-key-material rule forbids the same way it forbids
printing the secret itself.

#+begin_src bash
grep -c 'age1ytrm8ea' secrets/hosts/agents/peteches-automation-ssh.yaml  # 1 -- agents can read it
grep -c 'age1gcrgp0s' secrets/hosts/agents/peteches-automation-ssh.yaml  # 0 -- claude-workstation cannot
sops filestatus secrets/hosts/agents/peteches-automation-ssh.yaml        # encrypted / unencrypted
#+end_src

and that the moved file still holds *the same keypair* it always did — compare
fingerprints into variables and print only the verdict, since an ed25519 public
key is key material too (=sops -d <file>= by itself prints the whole decrypted
document, so it is never the check to run):

#+begin_src bash
umask 077; priv=$(mktemp); pub=$(mktemp)
sops -d --extract '["private-key"]' secrets/hosts/agents/peteches-automation-ssh.yaml > "$priv"
sops -d --extract '["public-key"]'  secrets/shared/peteches-automation-ssh-pub.yaml  > "$pub"
fp_priv=$(ssh-keygen -lf "$priv" | awk '{print $2}')
fp_pub=$(ssh-keygen -lf "$pub"  | awk '{print $2}')
[ -n "$fp_priv" ] && [ "$fp_priv" = "$fp_pub" ] && echo KEYPAIR_MATCH || echo KEYPAIR_MISMATCH
shred -u "$priv" "$pub"
#+end_src

Compare with =-l= (fingerprints), *not* with =ssh-keygen -e=: =-e= exports an
SSH2-format block (=---- BEGIN SSH2 PUBLIC KEY ----=), not the
=ssh-ed25519 AAAA...= line a stored public key holds, so a byte-wise comparison
of =-e= against a stored key is a guaranteed false negative even when the pair
matches — and =-e= additionally refuses a private key file that is group or
world readable (an =UNPROTECTED PRIVATE KEY FILE!= warning, and the PEM echoed
back as if it were the answer), while =-l= tolerates those permissions and just
prints the real fingerprint. That asymmetry is why the recipe pins =umask 077=
anyway: it is the only setting under which both variants agree.

Two other failure modes that look like a broken secret and are not:

- =sops -d= exits 128 with =Recovery failed because no master key was able to
  decrypt the file= when the operator PGP key's gpg-agent cache has expired
  (=default-cache-ttl= is 8h here). Unlock it in a real terminal —
  =gpg --sign -o /dev/null /dev/null= pops pinentry — and re-run; the file is
  fine.
- =ssh-keygen= refuses to *use* a private key file whose permissions are group
  or world readable: =-e= prints an =UNPROTECTED PRIVATE KEY FILE!= warning and
  echoes the PEM back instead of an answer, which makes a healthy keypair look
  like a mismatch. =umask 077= (or =mktemp=) above is what keeps that honest.

Rotating the keypair itself is a fleet-wide event, not a per-host one: re-encrypt
*both* halves (the shared one for every VM again) and redeploy every VM, since
every VM holds the public half, =agents= holds the private one, and both are
decrypted at boot.

* Claude Code account secrets

Claude Code accounts (e.g. =criticalgrind= on =claude-workstation=) sometimes
need dotenv-formatted secrets — API keys for MCP servers — rather than the
usual per-host YAML. These live alongside the other per-host secrets, just
with a =.env= extension, e.g. =secrets/hosts/claude-workstation/critical-grind.env=.

They carry *both* recipients: the VM's own age key, since they're decrypted
directly at system boot (see =#:sops-secrets= in
=peteches/systems/claude-workstation.scm=) into =/run/secrets/...= and exported
into the account's shell from there (see =#:secret-env-vars= in
=peteches/home/modules/claude-workstation.scm=); and the peteches operator PGP
key, purely so the file can also be edited from a desktop with gpg-agent.
Edit and re-key them like any other secret:

#+begin_src bash
sops secrets/hosts/claude-workstation/critical-grind.env
sops updatekeys secrets/hosts/claude-workstation/critical-grind.env
#+end_src

* WireGuard split-tunnel secret (claude-workstation)

=secrets/hosts/claude-workstation/wireguard.yaml= holds the *entire* wg-quick
config for claude-workstation's split-tunnel WireGuard interface as a single
key, =wg0-conf=, decrypted at boot straight to =/run/secrets/wg0.conf= (see
=#:sops-secrets= in =peteches/systems/claude-workstation.scm=). Nothing about
the tunnel -- private key, peer public key, endpoint, or tunnel address --
lives in any =.scm= file; the Guix side only knows the decrypted path. See
=(peteches services wireguard-socks5)= for how that path gets turned into a
running interface and a local SOCKS5 proxy (microsocks) that only tunnels the
traffic explicitly sent to it -- the VM's default route and DNS resolver are
left alone.

Edit it like any other secret:

#+begin_src bash
sops secrets/hosts/claude-workstation/wireguard.yaml
sops updatekeys secrets/hosts/claude-workstation/wireguard.yaml
#+end_src

=wg0= and microsocks both live inside their own network namespace (default
name =wg0ns=), connected to the host only by a veth pair -- see the module
docstring in =wireguard-socks5.scm= for the full picture. Because nothing
else lives in that namespace, the =wg0-conf= value needs none of the old
=Table = off= / fwmark / policy-routing PostUp/PreDown lines: a plain
=AllowedIPs = 0.0.0.0/0= default route already sends everything in the
namespace over the tunnel.

=DNS = <server>= *should* be set this time, and works as documented: before
=wg-quick= ever runs, =netns-wg0ns= seeds the namespace's private
=/etc/netns/wg0ns/resolv.conf= with just openresolv's own signature line
(=# Generated by resolvconf=, see =%openresolv-signature-line= in
=wireguard-socks5.scm=), which is enough for =resolvconf -a= (called by
wg-quick's =DNS=/PostUp handling) to recognise the file as already "owned"
and rewrite it with the real nameserver -- all inside the namespace's own
private resolv.conf, reached over the tunnel by the namespace's own default
route, never touching the host's (Tailscale-managed) resolver. This is the
same mechanism that made the *original* (pre-namespace) design fail against
Tailscale's resolv.conf -- it's just aimed at a file this design controls
instead of the host's:

#+begin_src conf
[Interface]
PrivateKey = <tunnel private key>
Address = <tunnel address>/32
DNS = <dns server reachable through the peer>

[Peer]
PublicKey = <peer public key>
Endpoint = <peer endpoint host:port>
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
#+end_src

The three shepherd services are named after the *netns*, not the interface:
=netns-wg0ns= (from the =netns= field, default ="wg0ns"=), =wireguard-wg0=
(from the =interface= field) and =socks5-proxy=. claude-workstation passes
=#:auto-start? #t= (see =peteches/systems/claude-workstation.scm=), so all
three come up on boot; on a machine without that flag they must be brought up
by hand, innermost last, and torn down outermost first:

#+begin_src bash
ssh claude-workstation sudo herd start netns-wg0ns
ssh claude-workstation sudo herd start wireguard-wg0
ssh claude-workstation sudo herd start socks5-proxy
# ... when done, outermost first:
ssh claude-workstation sudo herd stop socks5-proxy
ssh claude-workstation sudo herd stop wireguard-wg0
ssh claude-workstation sudo herd stop netns-wg0ns
#+end_src

** Recovering a tunnel that is up but never handshakes

=herd status= reporting =wireguard-wg0= *running* means only that
=wg-quick up= exited 0 -- it says nothing about the peer ever answering. Check
the peer's actual state, which =herd= cannot see:

#+begin_src bash
ssh claude-workstation sudo ip netns exec wg0ns wg show wg0 latest-handshakes
ssh claude-workstation sudo ip netns exec wg0ns wg show wg0 transfer
#+end_src

=0= in the =latest-handshakes= column (or =0B received= in =transfer) while
=PersistentKeepalive= keeps bytes going *out* is the signature of this failure:
the SOCKS proxy is listening and =proxychains4 nc= connects, so the ssh jump
hangs until ssh's own banner timeout, yet nothing about the local config is
wrong -- the UDP four-tuple that the peer (or the ISP's CGNAT in front of this
VM) mapped for the interface's old source port has gone stale, and the peer's
replies are being blackholed forever. =wg= retransmits indefinitely, so this
never self-heals; nothing here respawns or health-checks the tunnel either
(=respawn? #f= and =start= is a one-shot =wg-quick up=).

The fix is to recreate the interface so it gets a fresh four-tuple -- a full
=down= then =up= on =wireguard-wg0= alone is enough (=netns-wg0ns= stays up,
=socks5-proxy= must be restarted after it because it depends on
=wireguard-wg0=):

#+begin_src bash
ssh claude-workstation sudo herd stop socks5-proxy
ssh claude-workstation sudo herd stop wireguard-wg0
ssh claude-workstation sudo herd start wireguard-wg0
# verify latest-handshakes is no longer 0 before starting the proxy:
ssh claude-workstation sudo ip netns exec wg0ns wg show wg0 latest-handshakes
ssh claude-workstation sudo herd start socks5-proxy
#+end_src

Use =stop= then =start=, not =herd restart=: =restart= re-runs the dependent
=sops-secret-wg0-conf= one-shot, and its =resolvconf -a= / nscd side effects
can leave =wg0= half-configured (interface created, no private key, no
address) while shepherd still reports it running -- =wg show= then prints only
an =interface:= header with a =listening port=, which is how you can tell it
happened. If it does, =herd stop= + =herd start= again recovers it.

Reach the proxy from the host at the netns side of the veth
(=10.200.0.2:1080= by default), e.g. =curl --socks5-hostname
10.200.0.2:1080 https://example.com=.
