#+title: Secrets Management
#+author: Pete 'Peteches' McCabe

* Overview

Secrets (API tokens, passwords, Tailscale auth keys, etc.) are encrypted with
[[https://getsops.io/][SOPS]] using [[https://age-encryption.org/][age]] public-key encryption.  Each VM has a unique age keypair; SOPS
encrypts secrets so only the intended recipient VM(s) can decrypt them at boot.

The =sops-guix= channel provides =sops-service-type=, which is wired into VMs via
the =sops-secrets= parameter of =make-vm-os= in =peteches/systems/vm-base.scm=.

* Directory structure

#+begin_example
.sops.yaml              ← encryption rules (path regex → age recipients)
age-keys/               ← age public keys, one per VM
secrets/
  hosts/
    <vm-name>/          ← per-host encrypted YAML files
  groups/
    concourse/          ← secrets shared by the Concourse cluster
    media/              ← secrets shared by media-stack VMs
  shared/
    tailscale.yaml      ← Tailscale auth key (shared)
#+end_example

* Age keys

Each VM generates its own age keypair on first boot (via the SOPS key generator
service in =vm-base.scm=).  The public key is committed to =age-keys/<vm-name>.pub=
so that new secrets can be encrypted for that VM without needing its private key.

The private key lives only on the VM itself (=/etc/age/key.txt= or similar);
it is never committed.

** Adding a key for a new VM

After the VM's first boot, retrieve and commit its public key:

#+begin_src bash
ssh <vm-name> cat /etc/age/key.txt | age-keygen -y   # prints public key
# DO NOT echo the private key — store only the public key:
# age-keys/<vm-name>.pub
#+end_src

Then add the appropriate =creation_rules= entry to =.sops.yaml=.

* Editing secrets

#+begin_src bash
sops secrets/hosts/<vm-name>/foo.yaml      # opens $EDITOR, re-encrypts on save
sops secrets/groups/media/credentials.yaml
#+end_src

SOPS reads encryption rules from =.sops.yaml= automatically.  The PGP key
=5FFB7006A36B0AEDE8D08E3753B1E002546A642A= (peteches operator key) is always
included as an additional recipient so secrets remain accessible from the
developer machine.

* Wiring secrets into a VM OS config

In the VM's system file, pass =sops-secrets= to =make-vm-os=:

#+begin_src scheme
(make-vm-os
  ...
  (sops-secrets (list "secrets/hosts/myvmname/foo.yaml")))
#+end_src

The =sops-service-type= will decrypt those files at activation time and make them
available to services on the VM.

* Group secrets

Some secrets are shared across multiple VMs.  Groups are defined in =.sops.yaml=
with a list of age recipients:

- =secrets/groups/concourse/= — shared by =concourse-web01= (other Concourse nodes
  get what they need via the web node)
- =secrets/groups/media/= — shared by jellyfin, prowlarr, arr, downloads, rustdesk

* Shared secrets

=secrets/shared/tailscale.yaml= contains the Tailscale auth key used by VMs that
run Tailscale.  It is encrypted for all Tailscale-enabled VM recipients.

* Claude Code account secrets

Claude Code accounts (e.g. =criticalgrind= on =claude-workstation=) sometimes
need dotenv-formatted secrets — API keys for MCP servers — rather than the
usual per-host YAML. These live alongside the other per-host secrets, just
with a =.env= extension, e.g. =secrets/hosts/claude-workstation/critical-grind.env=.

They carry *both* recipients: the VM's own age key, since they're decrypted
directly at system boot (see =#:sops-secrets= in
=peteches/systems/claude-workstation.scm=) into =/run/secrets/...= and exported
into the account's shell from there (see =#:secret-env-vars= in
=peteches/home/modules/claude-workstation.scm=); and the peteches operator PGP
key, purely so the file can also be edited from a desktop with gpg-agent.
Edit and re-key them like any other secret:

#+begin_src bash
sops secrets/hosts/claude-workstation/critical-grind.env
sops updatekeys secrets/hosts/claude-workstation/critical-grind.env
#+end_src

* WireGuard split-tunnel secret (claude-workstation)

=secrets/hosts/claude-workstation/wireguard.yaml= holds the *entire* wg-quick
config for claude-workstation's split-tunnel WireGuard interface as a single
key, =wg0-conf=, decrypted at boot straight to =/run/secrets/wg0.conf= (see
=#:sops-secrets= in =peteches/systems/claude-workstation.scm=). Nothing about
the tunnel -- private key, peer public key, endpoint, or tunnel address --
lives in any =.scm= file; the Guix side only knows the decrypted path. See
=(peteches services wireguard-socks5)= for how that path gets turned into a
running interface and a local SOCKS5 proxy (microsocks) that only tunnels the
traffic explicitly sent to it -- the VM's default route and DNS resolver are
left alone.

Edit it like any other secret:

#+begin_src bash
sops secrets/hosts/claude-workstation/wireguard.yaml
sops updatekeys secrets/hosts/claude-workstation/wireguard.yaml
#+end_src

=wg0= and microsocks both live inside their own network namespace (default
name =wg0ns=), connected to the host only by a veth pair -- see the module
docstring in =wireguard-socks5.scm= for the full picture. Because nothing
else lives in that namespace, the =wg0-conf= value needs none of the old
=Table = off= / fwmark / policy-routing PostUp/PreDown lines: a plain
=AllowedIPs = 0.0.0.0/0= default route already sends everything in the
namespace over the tunnel.

=DNS = <server>= *should* be set this time, and works as documented: before
=wg-quick= ever runs, =netns-wg0= seeds the namespace's private
=/etc/netns/wg0ns/resolv.conf= with just openresolv's own signature line
(=# Generated by resolvconf=, see =%openresolv-signature-line= in
=wireguard-socks5.scm=), which is enough for =resolvconf -a= (called by
wg-quick's =DNS=/PostUp handling) to recognise the file as already "owned"
and rewrite it with the real nameserver -- all inside the namespace's own
private resolv.conf, reached over the tunnel by the namespace's own default
route, never touching the host's (Tailscale-managed) resolver. This is the
same mechanism that made the *original* (pre-namespace) design fail against
Tailscale's resolv.conf -- it's just aimed at a file this design controls
instead of the host's:

#+begin_src conf
[Interface]
PrivateKey = <tunnel private key>
Address = <tunnel address>/32
DNS = <dns server reachable through the peer>

[Peer]
PublicKey = <peer public key>
Endpoint = <peer endpoint host:port>
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
#+end_src

None of the three shepherd services start automatically (on boot or =herd
reload=) -- bring the tunnel up manually when you actually want it, innermost
last:

#+begin_src bash
ssh claude-workstation sudo herd start netns-wg0
ssh claude-workstation sudo herd start wireguard-wg0
ssh claude-workstation sudo herd start socks5-proxy
# ... when done, outermost first:
ssh claude-workstation sudo herd stop socks5-proxy
ssh claude-workstation sudo herd stop wireguard-wg0
ssh claude-workstation sudo herd stop netns-wg0
#+end_src

Reach the proxy from the host at the netns side of the veth
(=10.200.0.2:1080= by default), e.g. =curl --socks5-hostname
10.200.0.2:1080 https://example.com=.
