#+title: Fleet Deployment
#+author: Pete 'Peteches' McCabe

* Overview

"Fleet deployment" means pushing a Guix configuration change out to some or
all of the VMs listed in =peteches/machines.scm= via =guix deploy=. This
document is the single source of truth for four questions that were
previously answered ad hoc, which is how the fleet ended up in an
inconsistent state (some VMs on a generation from Aug 31, most still on one
from Aug 23, with no record of why):

1. *When* a deploy is required, and to which hosts.
2. *How* it is carried out (skill usage, not raw commands).
3. *How success is verified*, per host.
4. *How to roll back* a host that fails or misbehaves after deploying.

Read this before running any deploy that touches more than the one VM you
happen to be looking at.

* When to deploy

The blast radius of a change determines who needs a deploy, not which file
you happened to be editing when you made it.

| Change touches                                                             | Who must be deployed                                  |
|------------------------------------------------------------------------------+--------------------------------------------------------|
| A single =peteches/systems/<name>.scm=                                     | Just =<name>=                                          |
| A shared module: =peteches/systems/vm-base.scm=, =common.scm=, =base.scm=  | Every VM built from that constructor (all VMs for =vm-base.scm=; dagon/nyarlothotep for =base.scm=) |
| A service *type* in =peteches/services/= or =peteches/home/services/=      | Every host whose system/home config extends that service |
| A package in =peteches/packages/=                                          | Every host whose config installs that package          |
| A channel pin bump (=peteches/channels/*.scm=)                              | The *entire fleet* — a channel bump changes what every subsequent build resolves to, even for hosts whose own =.scm= file didn't change |
| =peteches/home/modules/= (home-environment fragments)                      | The desktops (dagon, nyarlothotep) reconfigured locally, plus every headless VM that has a home-environment — currently claude-workstation and agents (both built by =(peteches home modules vm-jumpbox)=) |

Rules:

- *Deploy promptly after merge.* A shared-module or channel change that
  lands on =main= but is only deployed to the host someone happened to be
  testing is exactly how the fleet drifts. Finish the fleet deploy in the
  same session as the merge, not "later."
- *Don't cherry-pick hosts for a fleet-wide change.* If the change's blast
  radius (table above) says "every VM," deploy to every VM that answers to
  a liveness check (see Step 2 of the skill below), not just the ones you
  personally care about right now. A host that's down at deploy time is
  *skipped and recorded*, not silently left off the target list.
- *Don't bundle unrelated changes into one fleet deploy.* If you're deploying
  a channel bump, don't also sneak in an unrelated single-host tweak in the
  same run — if the run fails partway, you want a clean rollback story (see
  "Rollback" below), and that's much harder when the diff being deployed is
  a grab-bag.
- A single-host change (row 1) can be deployed whenever convenient; it has
  no fleet-consistency implication.

* How to deploy

*Always use the =deploy-vms= skill* (=.claude/skills/deploy-vms/=) instead of
calling =scripts/deploy.scm= or =guix deploy= directly. This is not a style
preference — the skill exists specifically to close two gaps that raw
invocations don't handle:

- *Host-name anchoring.* A bare =--hosts arr= substring-matches =prowlarr=
  too. The skill always anchors on the exact =<name>-machine= variable name.
- *Isolation and reporting.* Each host is deployed in its own invocation, so
  one failing host doesn't abort or obscure the rest, and you get a
  pass/fail table at the end instead of interleaved output from a combined
  run.

Usage:

#+begin_src text
deploy-vms                      # whole fleet, one host at a time
deploy-vms git loki grafana     # only the named hosts
deploy-vms comfyui --dry-run    # passthrough args forwarded verbatim
#+end_src

Per the skill's own rules: confirm full-fleet scope with the user before
starting if it wasn't unambiguous that "everything" was intended, run hosts
strictly sequentially (never in parallel — they share this machine's
=guix-daemon= and substitute cache), and don't let one unreachable or
failing host stop the rest of the list.

Before kicking off a fleet-wide deploy for a shared-module or channel
change, sanity-check the build locally first so a typo doesn't get
discovered independently on 15 different VMs:

#+begin_src bash
guix system build -L . --dry-run peteches/systems/<any-affected-host>.scm
#+end_src

** Which box a fleet deploy runs from

A deploy needs *two* independent credentials on the box that runs it, and
only one of them is an SSH key:

1. *A login identity every target accepts.* Either a desktop's own
   =~/.ssh/id_ed25519= (dagon and nyarlothotep each have one, and both are
   enrolled in every VM's =%vm-peteches-authorized-keys=), or the private half
   of the fleet-wide *peteches automation keypair*, whose public half every VM
   also authorizes for the peteches login (=vm-base.scm='s
   =%automation-authorized-key-secret= plus its sshd =Match= block). Since
   2026-11-05 that private half is decrypted on =agents= only (its
   =#:sops-secrets= entry); =claude-workstation= held it first and lost it
   when it became a pure WireGuard/SOCKS jump box, so that box has no outbound
   identity at all now. =machines.scm='s =%deploy-identity= picks whichever of
   the two paths exists on the host running the deploy.
2. *That box's own =guix-daemon= signing key*, listed in
   =%authorize-coordinator-key= (=peteches/systems/common.scm=). =agents=,
   =dagon= and =nyarlothotep= are listed. A coordinator that is not listed
   still connects, still sends the closure and still switches the target's
   generation — but its deploy then fails on the last step, so listing is not
   optional for a box meant to deploy (see §4 below).

=agents= has no =~/area_51/guix= checkout today (checked live 2026-11-05), and
neither does =claude-workstation=, so until somebody clones the repo on
=agents= the skill still runs from a desktop. That clone is the only piece
missing there — its deploy key, its =known_hosts2= for the fetch and its
coordinator entry in =common.scm= are all in place.

Build-wise =agents= is now fully wired to the offload farm — both halves of its
offload keypair (ssh and archive-signing) were verified against the box and
added to =guix-build.scm= on 2026-11-05, so a deploy run from there pushes its
closures to =guix-build= instead of building them locally. Running the same
deploy from dagon does the opposite: dagon has no offload keypair at all (no
=secrets/hosts/dagon/guix-build.yaml=), so every closure a desktop-origin
deploy needs is built on that desktop's own daemon — see “The build-offload
keypairs drift separately” below.

* Verifying success, per host

A deploy that exits =0= is necessary but not sufficient — =scripts/deploy.scm=
exiting cleanly only means the SSH session and the store transfer succeeded,
not that the intended service is actually serving. Check both.

** 1. Generation actually advanced

Run these checks *from the box that holds the deploy identity*. Since
2026-11-05 that is =agents= — its =peteches= account decrypts the private half
of the automation keypair to =/run/secrets/peteches-automation-ssh-key=, and
=-i= has to be passed by hand there because no fleet SSH config is deployed to
that account, so neither the VMs' short names nor =.ts= aliases resolve, and
the key is not in an ssh-agent. A desktop works too and needs no =-i= at all:
from dagon the fleet resolves through =~/.ssh/config= and the =id_ed25519=
there is authorized on every VM (=claude-workstation= is the one box that can
no longer do this at all — it has neither key any more):

#+begin_src bash
ssh -i /run/secrets/peteches-automation-ssh-key peteches@<lan-ip> \
    'guix system describe 2>&1 | head -1'
#+end_src

Expect a generation number/timestamp *newer* than the one recorded before
the deploy started. A stray =/etc/profile: line 9: ... No such file or
directory= line ahead of the real output is a harmless warning from that
line sourcing a not-yet-linked extensions directory — ignore it, don't treat
it as a failure.

Use the VM's LAN IP from =proxmox-vms.org=, not its hostname — this account
has no =~/.ssh/config= entries for the fleet's short names or =.ts= aliases.

** 2. The service actually restarted, not just the config

Generation-bump alone doesn't prove the *service* picked up the change — a
config swap that isn't followed by a live reload (see the ACL-gap failure
mode below) leaves the *old* process serving on a correctly-updated =/etc=,
and a port/health check in that state still reports healthy. Compare the
service's process start time against the generation switch time:

#+begin_src bash
# when the current generation was switched to
stat -c '%y' /var/guix/profiles/system
# when the service process actually started, and what store path it's running
sudo herd status <service>
#+end_src

If =herd status='s "It is running since ..." time is *before* the
generation-switch time, the service is still running the old configuration
regardless of what =/etc= or =guix system describe= say — run
=sudo herd restart <service>= and re-check. Only once the process start
time is *after* the generation switch is it safe to trust the port/health
check below as evidence the *new* config is what's actually serving.

** 4. Known failure mode: shepherd-reload ACL gap

Any deploy run from a box whose =guix-daemon= signing key is *not* in the
target's declarative ACL ends with:

#+begin_example
guix deploy: error: unauthorized public key: (public-key ...)
#+end_example

on the *final* step (the live =upgrade-shepherd-services= archive send) —
even though the new generation and =/etc= were already switched over
correctly by the steps before it. This is a store-archive trust (ACL) gap
(the coordinator's =guix-daemon= signing key isn't in the target's
=/etc/guix/acl=), not an SSH/login failure — and note *why* it happens even
though =guix deploy= authorizes the coordinator's key itself first
(=(gnu machine ssh)='s =authorize?= field, default =#t#=): the
=switch-to-system= that follows rebuilds =/etc/guix/acl= from the target's own
declarative =authorized-keys= list, so any key absent from
=%authorize-coordinator-key= is revoked again before that last send, and
adding it by hand on the target only holds until the next deploy.

=claude-workstation= is the box this failure mode was named for, until its
deploy role ended on 2026-11-05 — its key was then *removed* from
=%authorize-coordinator-key= (it had gone stale anyway: that VM was rebuilt
from the MinIO image on 2026-10-27 and its =/etc/guix/signing-key.pub= changed
with the image — see the registry table below). =agents= is the VM in that
list now. The rule for anything new: a box meant to deploy has to be in
=common.scm='s list *before* the first deploy from it is expected to finish
cleanly.

*** Coordinator signing-key registry — current state, audited 2026-11-05

Hashes below are *not* the whole-file =sha256sum=. Compute them the same way on
both sides or they are not comparable: the stable identity of a guix archive
key is the set of =#…#= fingerprint tokens it is built from, so hash *those*:

#+begin_src bash
grep -o '#[0-9A-Fa-f]*#' <file> | sha256sum | cut -c1-10
#+end_src

A whole-file =sha256sum= of the same key gives a different number depending on
trailing whitespace — which is how a "verified" key can quietly stop matching.

| Coordinator          | Committed key                                            | Live on the box  | Status                                                |
|----------------------+----------------------------------------------------------+------------------+--------------------------------------------------------|
| dagon                | =d43223e08f= in =common.scm=                             | =d43223e08f=     | ✅ MATCH — verified by hashing =/etc/guix/signing-key.pub= on dagon itself |
| agents               | =eed65f7d40= in =common.scm=                             | =eed65f7d40=     | ✅ MATCH — verified live over ssh on 2026-11-05, the day its entry was added |
| nyarlothotep         | =04f0a01446= in =common.scm=                             | *not sampled*    | ⚠️ UNVERIFIED — unreachable 2026-11-05 on *both* its Tailscale name and LAN =192.168.50.10= (tcp/22 timeout on each), so its committed key is taken on trust; re-sample when the box is back |
| claude-workstation   | *none in fleet config* — removed from =%authorize-coordinator-key= on 2026-11-05 when it stopped being a deploy origin | =543f3b13f0=     | ✅ RESOLVED 2026-11-05 — the VM was rebuilt from the MinIO image on 2026-10-27, and =/etc/guix/signing-key.pub= is baked into that image, so the =7b9d70cae1= text this table used to show (inherited from =nug=) no longer existed anywhere on the box. Its stale copy in =guix-build.scm='s =guix-offload-signing-keys= — the only place it still appeared — was replaced with the live key the same day. =7b9d70cae1= now survives only in git history |

One more drift the same audit turned up, because it is the easy miss: the
registry is *two* lists that drift independently — the archive-signing keys
above, and the age keys in =age-keys/= that decide who can decrypt a secret.
=jellyfin= was the one confirmed case, and it is now fixed: its live
=/etc/age/keys.pub= (the per-VM own age key — there is no =keyring.pub= on that
box, checked 2026-11-05) did *not* match committed =age-keys/jellyfin.pub=, while
=.sops.yaml='s =secrets/shared/.*\.yaml$= rule and every already-encrypted
=secrets/shared/= file carried the *live* key — which is why that VM decrypted
=secrets/shared/peteches-automation-ssh-pub.yaml= happily at boot and why the
mismatch was invisible. Encrypting a *new* secret for jellyfin from the stale
file would have produced one that VM cannot read. It was refreshed from the box
on 2026-11-05 over an ssh connection verified against =machines.scm='s pinned
host key, and hash-checked before and after, so the committed file and the live
one now agree. =dagon.pub= is likewise absent from that rule — expected, a desktop is
not a =make-vm-os= VM and reaches every secret through the operator PGP
recipient instead. Re-check both lists after **any** VM rebuild or
re-provision; that is exactly the event that invalidates a key that looked
fine the week before.

The same recount also shows the shared rule carries age keys that have **no**
committed =age-keys/*.pub= file (22 recipients against 23 committed files, with
=dagon.pub= expected to be absent from the recipients), so a recipient audit
against =age-keys/= can never be complete, and a recipient with no committed
file cannot be re-keyed from the repo at all.

When you see this: don't report the deploy as failed outright. Check §1
above — the generation almost always did advance. If §2's restart check
shows the process predates the switch, the service needs a live reload it
never got — SSH in and finish it by hand:

#+begin_src bash
ssh -i /run/secrets/peteches-automation-ssh-key peteches@<lan-ip> \
    'sudo herd reload <service>'   # or 'restart' if the service has no reload action
#+end_src

Note in the deploy report which hosts needed this manual step.

** 5. Files activation writes — stale after a deploy that never rebooted

=guix deploy= switches the generation, sends the closure and reloads the
shepherd services it thinks changed, but **it does not run the activation
snippets** — those hang off =activation-service-type=, which extends
=boot-service-type= (=gnu/services.scm=: =gexp->activation-gexp=,
=(activate-current-system)= then =for-each primitive-load= over the
per-service =activate-service.scm= items, each failure tolerated with a
="failed to activate"= warning), so they run at **boot** and at
=sudo guix system reconfigure=, not at =switch-system= without a reboot.
Any file a service's activation generates — =/var/lib/strata/run-strata.sh=
and =ze_intel_gpu.icd.json= under that service, and the same class of
state for anything else that writes files rather than =/etc= — keeps its
**old content** with a green deploy report, and neither §2 nor §3 catches
it: the service can have restarted cleanly *into the current generation*
and still be running the config the old generated file encodes.

The tell is the file's mtime against the generation-switch time:

#+begin_src bash
stat -c '%y' /var/guix/profiles/system   # generation switch
sudo stat -c '%y %s %n' <the generated file>
#+end_src

If the file predates the switch, activation never ran. Two ways to finish
it, in preference order:

#+begin_src bash
sudo /run/current-system/activate        # re-runs every snippet; idempotent
                                         # expect a few hundred bytes of output
                                         # and no "failed to activate" lines
sudo herd restart <service>              # now it picks up the regenerated file
sudo reboot                              # or just reboot, if one was due anyway
#+end_src

To find which snippet a service's activation is, take the list of store
paths embedded in the current activation script and grep them:

#+begin_src bash
sudo grep -o "/gnu/store/[a-z0-9]\{32\}-activate-service\.scm" \
     "$(sudo readlink -f /run/current-system/activate)" | sort -u
sudo grep -l -- "<a string only the new config emits>" <those paths>
#+end_src

That last grep is also the positive check: it says whether the deployed
generation really contains the change *before* blaming the file. Worked
example, comfyui 2026-10-30: generation 61 went in at 18:27 with shepherd
reloads and =/run/current-system= updated, yet =run-strata.sh= still
carried a 15:59 mtime and no =--vision= — its activation snippet
*did* contain =--vision= (found by the recipe above), proving the deploy
was fine and that only the boot-time activation was missing.

* The build-offload keypairs drift separately from everything above

Offload to =guix-build= depends on /two/ more keypairs per box, checked by two
different daemons, so they drift on their own schedule and independently of the
coordinator registry:

| Half                       | Where it must be authorized                             | What happens when it is stale or missing              |
|----------------------------+---------------------------------------------------------+------------------------------------------------------|
| SSH =guix-offload= keypair | =guix-build.scm= =guix-offload-authorized-keys=          | ssh connection refused — =guix= reports it as an offload failure |
|                            | (source: =/etc/guix/offload/guix-build.pub= per box,     |                                                      |
|                            | matching =secrets/hosts/<vm>/guix-build.yaml=)           |                                                      |
| Box's =signing-key.pub=    | =guix-build.scm= =guix-offload-signing-keys=             | =unauthorized public key= at the archive send; the build |
|                            | (the =guix-extension= =authorized-keys=)                 | falls back to building locally, so nothing visible breaks |

Before 2026-11-05 the ssh half had been kept roughly current while the archive
half held /one/ key (claude-workstation's), and that one had gone stale when the
box was rebuilt from the MinIO image on 2026-10-27 — so offload from
claude-workstation had been falling back to local builds silently for weeks and
every other intended offloader was missing outright. That silent-fallback
behavior is why the gap survived: offload *looked* like it was working (it
connected, ssh auth passed) and only the archive send failed, which =guix=
reports as an ordinary build failure.

Both halves are now populated from live, host-key-verified material. The archive
list carries the live signing key of every box with a verified offload keypair
(agents, arr, caddy, claude-workstation, the three Concourse boxes, downloads,
git, grafana, jellyfin, loki, pihole, prometheus, prowlarr), each entry
hash-checked against that box's =/etc/guix/signing-key.pub= at the time of
writing, and the ssh list gained the four boxes that had an offload keypair but
no ssh entry (=agents= and the three Concourse boxes, each checked against the
box's live =/run/secrets/guix-offload-key=).

Failure modes worth knowing before touching this list:

- =ssh-keygen -y= on a private key refuses to run when the key file is group or
  world readable, which is how =/run/secrets/guix-offload-key= can land after
  some activations — =ssh-keygen -e= on the same file still echoes the PEM, so
  "it reads" is not evidence the derived key is sound. Copy it with mode =0600=
  and derive from the copy.
- That permission check is also where offload diagnostics lie, because
  `/run/secrets/<path>` is a **symlink** the sops service creates into
  `/run/secrets/<sops-key-name>` — the configured `permissions` live on the
  target, not on the link. Measured on =agents= 2026-11-05:
  `sudo stat -c "%a %n" /run/secrets/guix-offload-key` reported `777` (the link)
  while `sudo stat -Lc "%a %U"` reported `400 root`, and the same pair of probes
  showed `/run/secrets/peteches-automation-ssh-key` → `400 peteches` ✓. Use
  `stat -L` whenever a `/run/secrets` mode matters, and note that
  `sudo ssh-keygen -y -f /run/secrets/<path>` is refused on the symlink while
  `ssh -i` with the very same path authenticates fine — so derive public keys
  from a mode-`0600` copy rather than from the symlink, and treat a refused
  `ssh-keygen` as a probe artifact until you have retried it on a copy.
- =ssh-keygen -e= emits *SSH2* format (=---- BEGIN SSH2 PUBLIC KEY ----=, base64
  of an ASN.1 wrapper), not the =ssh-ed25519 AAAA…= line =authorized_keys= and
  =machines.scm= use, so byte-comparing an =-e= blob against a committed entry
  is a guaranteed false negative. Compare fingerprints (=ssh-keygen -lf=) or the
  first two fields of a =-y=-style line.
- Some boxes have /no/ offload keypair at all (=vault=, =plane=, =comfyui=,
  =dagon=, =agents= before 2026-11-05, =critical-grind-*=): offload from them
  cannot even authenticate as =guix-offload=, their signing keys are
  deliberately absent, and =#:with-nug-offload? #t= on them is aspirational
  rather than wired.
- =rustdesk= and =nyarlothotep= are the reverse gap: both /are/ in the ssh list
  and /both/ have an offload keypair, but neither box was reachable on
  2026-11-05, so no verified signing key could be added — their offload keeps
  falling back to local builds until one is fetched. nyarlothotep is the
  asymmetry to watch for: its ssh half is authorized and its archive half is
  not, and those two trusts only stay in step if somebody keeps them there by
  hand.
- =guix-build= itself does not use =make-vm-os='s =#:with-nug-offload?= hook (it
  passes =#:with-nug-offload? #f= and defines its own offload user and both key
  lists), and its own keypair is generated on the box, so =guix-build='s key
  appears in no file in this repo.

To re-audit the whole set in one pass, derive each box's two public halves from
the box itself — never from a copy — and hash instead of printing:

#+begin_src bash
ssh <host> 'cat /etc/guix/signing-key.pub' > /dev/shm/$h.signing.pub   # public material
ssh <host> 'umask 077; sudo install -m 600 /run/secrets/guix-offload-key /tmp/k.$$$$ \
            && sudo ssh-keygen -y -f /tmp/k.$$$$; sudo rm -f /tmp/k.$$$$' > /dev/shm/$h.offload
ssh-keygen -lf /dev/shm/$h.signing.pub | awk '{print $2}'              # fingerprint only
#+end_src

* Rollback

=guix deploy= has no built-in "undo" — rollback happens on the target VM
using generations that are already in its profile, which is faster and
safer than trying to redeploy an old commit from here.

** Single host

#+begin_src bash
ssh -i /run/secrets/peteches-automation-ssh-key peteches@<lan-ip>   # from agents; from a desktop, ssh peteches@<ip> with no -i
sudo guix system list-generations      # find the last-known-good number
sudo guix system roll-back             # steps back exactly one generation
# or, to jump to a specific one:
sudo guix system switch-generation <N>
sudo reboot                            # only if the failure involves the kernel/bootloader;
                                        # a service-level regression usually just needs:
sudo herd restart <service>
#+end_src

After rolling back, re-run the §"Verifying success" checks against the
rolled-back generation to confirm it's actually healthy — a generation can
be "last known good" and still have drifted (e.g. an expired cert) since it
was current.

** Fleet-wide change

If a shared-module or channel-wide deploy causes problems on multiple hosts,
don't roll back each VM individually as the first response — first decide
whether the fix is "revert the commit and redeploy" or "roll back each
affected VM's generation":

- *Revert + redeploy* is preferred when the bad change hasn't finished
  rolling out to the whole target list yet, or when you want =main= to stop
  matching the bad config (so nobody accidentally deploys it again). Revert
  in git, then run =deploy-vms= again against the same host list.
- *Per-VM =guix system roll-back** is faster when the change is already live
  everywhere and you need service back immediately; it doesn't touch git
  history, so remember the repo's =HEAD= still contains the bad commit until
  someone reverts it — the next unrelated fleet deploy could reintroduce the
  regression if this isn't followed up.

Either way, record which hosts were rolled back and which were redeployed —
don't leave the fleet in a mixed state without noting it, which is the exact
problem this document exists to prevent.

* Fleet consistency audit

Periodically (and always immediately after a fleet-wide deploy), confirm
every reachable VM is actually on the generation you expect, rather than
assuming a deploy that reported success actually landed everywhere. This is
the check to run when asked to "check the fleet" or "when was the last
deploy":

Run it from =agents=, the box that now holds the automation key the =-i=
below names. From a desktop drop =-i= — the =id_ed25519= there is authorized
on every VM too — but expect to confirm host keys on first contact by bare
IP, because a desktop's =known_hosts= is keyed by the fleet's names rather
than their addresses.

declare -A ips=(

Interpreting results:

- A generation/timestamp: host is up and reporting current state. Compare
  timestamps across the fleet — outliers (much older than the rest after a
  fleet-wide change) are the drift this document exists to prevent.
- =ssh: connect ... No route to host= *and* the IP doesn't answer =ping=
  either: the VM is powered off, not a deploy/SSH problem. Confirm in the
  Proxmox console before treating it as a failed deploy.
- =Permission denied (publickey,password)=: the automation key genuinely
  isn't authorized on that host — different problem from "powered off,"
  investigate separately (this is not the ACL-gap failure mode in
  §"Verifying success", which manifests as a =guix deploy=-time error, not
  an SSH login failure).

IPs and short names above are current as of this writing; =proxmox-vms.org=
is the authoritative source if the fleet has grown — regenerate the
association array from there rather than trusting a stale copy indefinitely.
